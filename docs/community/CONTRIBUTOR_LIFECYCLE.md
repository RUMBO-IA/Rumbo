# RUMBO contributor lifecycle

This document defines how participation can grow without granting more authority than the work requires.

## Stage 0 — Visitor

Can read public material, open an Issue, join a public Discussion when enabled, or participate in community chat.

Repository access: none beyond normal public GitHub access.

## Stage 1 — Public contributor

Works from a personal fork and opens pull requests to the Open Lab.

Repository access: no organization membership and no upstream write permission required.

Suitable for nearly all first contributions.

## Stage 2 — Community triage

Intended for a contributor who repeatedly helps classify Issues, answer questions, reproduce problems, or organize public Discussions.

Preferred GitHub role: **Triage**, because it permits issue/discussion/PR coordination without source write access.

Promotion requires an explicit maintainer decision and readback of the assigned repository role.

## Stage 3 — Public maintainer

Intended for sustained maintainers of the public repository.

Use **Write** only when direct branch work is actually necessary. Use **Maintain** only for repository-management duties that do not require Admin.

This role remains separate from canonical/private authority.

## Stage 4 — Closed Lab collaborator

Used when a bounded private project genuinely requires non-public source collaboration.

Default placement: dedicated private Closed Lab repository, repository-scoped access, minimum role necessary.

Outside-collaborator access is preferred when the person does not need broader organization membership.

Closed Lab does not inherit production credentials, canonical private repository access, customer data, or deployment authority.

## Stage 5 — Core maintainer

Core/canonical access is a separate governance decision. It is never an automatic reward for community contribution, seniority, employment, contracting, or Closed Lab access.

Core access requires a defined business need, explicit owner authorization, minimum privilege, and offboarding coverage.

## Promotion evidence

Before any access increase, record:

1. GitHub login;
2. requested repository;
3. exact role;
4. reason the lower role is insufficient;
5. start/review date;
6. owner approving the change;
7. readback after assignment.

## Offboarding

When a collaboration ends or scope shrinks, verify:

- repository membership and outside-collaborator access;
- team membership;
- pending invitations;
- tokens and app grants issued for the engagement;
- SSH/deploy keys;
- Codespaces or remote workspaces;
- Actions environments and secrets;
- external SaaS access;
- AI-tool credentials or shared workspaces;
- any local or cloud copies of non-public project data.

Access removal must be verified by readback, not assumed from an invitation or employment status change.
